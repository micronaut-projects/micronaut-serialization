By default, a property naming strategy applies to both serialization and deserialization. Use `@Serdeable.Serializable` and `@Serdeable.Deserializable` when the JSON written by an application must follow a different naming convention from the JSON it reads.

The following type writes snake case property names and reads upper camel case property names:

snippet::example.DirectionalContact[project-base="doc-examples/example", source="main"]

<1> The serialization naming strategy converts `firstName` and `lastName` to `first_name` and `last_name`.
<2> The deserialization naming strategy expects `FirstName` and `LastName`.

For example, serializing the type produces:

[source,json]
----
{"first_name":"John","last_name":"Doe"}
----

The same type can deserialize JSON that uses the input naming convention:

[source,json]
----
{"FirstName":"Jane","LastName":"Smith"}
----

Directional naming can be declared on a type or on an individual property, with the same rules at both levels. Explicit property names take precedence over naming strategies.

IMPORTANT: For backward compatibility, a naming strategy declared on only one of `@Serdeable.Serializable` and `@Serdeable.Deserializable` still applies to both directions, as it did before directional naming was introduced. Naming is directional when both annotations declare a strategy, or when one of them overrides a shared naming strategy such as `@Serdeable(naming = ...)` or `@JsonNaming`. To change the names in one direction only, declare `IdentityStrategy` on the other annotation, for example `@Serdeable.Serializable(naming = SnakeCaseStrategy.class) @Serdeable.Deserializable(naming = IdentityStrategy.class)`.

Use `@Serdeable(naming = ...)` when the same naming strategy should apply in both directions. A type whose properties are written and read with different names is handled by the runtime serializers and deserializers rather than the source-generated ones.
